# LawFirmAgent Web App (local prototype)

A small local web app: upload a `.zip` of PDFs, it extracts text from each one, sends them to the
local Ollama model with the chronology-building prompt in `prompts/chronology_prompt_structured.txt`,
and shows the result in the browser as a two-pane view — findings on the left, a PDF viewer on the
right that jumps to and highlights the exact source passage when you hover a finding. Runs entirely on
`127.0.0.1` — nothing leaves this machine.

**Prototype only.** Do not upload real case files or PHI until firm IT/compliance has formally
approved this project (`PRODUCT_DEFINITION.md` §7/§9). Use synthetic/test PDFs.

## Running it

Requires the Ollama server already running (it auto-starts on login via the LaunchAgent set up
earlier — check with `launchctl list | grep lawfirmagent`) and the `llama3.1:8b` model pulled.

```
cd webapp
.venv/bin/python app.py
```

Then open **http://127.0.0.1:5050** in a browser. Upload a zip of PDFs and click "Build Chronology."
A run over ~9 short documents takes about a minute on this machine (M3, 16GB) — expect longer with
more/larger documents.

To stop it, find and kill the process: `pgrep -fl "app.py"` then `kill <pid>`.

## Try it with the ready-made test case

`sample_data/case_001_pdfs.zip` (generated by `scripts/make_test_pdfs.py` from the synthetic case in
`sample_data/case_001_raw_records.md`) is a ready-made 9-PDF zip you can upload immediately to see it
work, with `sample_data/case_001_answer_key.md` as the known-correct answer to check the output against.

## How it works

1. Zip is extracted into a per-analysis session folder (system temp dir, named with a random id).
   Progress streams to the browser live as each PDF is processed.
2. Each PDF's text is pulled out page-by-page with `pdfplumber` (handles multi-column/irregular
   layouts noticeably better than a plain text-extraction library). Any page whose text layer is
   missing or too sparse to be useful (a scanned/faxed record with no embedded text at all) falls
   back to OCR: the page is rasterized and run through `easyocr` (pure-Python, no system OCR binary
   required). A page is only excluded if even OCR yields nothing readable. Files where OCR kicked
   in are flagged with a warning so you know to double-check those findings more carefully — OCR
   is noticeably less reliable than a native text layer (digit/letter confusion, dropped
   punctuation). See `PRODUCT_DEFINITION.md` §6 for the still-unbuilt vision-model OCR option
   (better on messy/handwritten scans, heavier resource cost).
3. All extracted document text goes into one prompt sent to the local model via Ollama, using a JSON
   schema (`format` field in the Ollama API) so the response comes back as structured data — a list of
   timeline events, potential issues, and discrepancies — rather than a loose block of prose. Every
   finding includes a `quote`: a verbatim excerpt the model was instructed to copy exactly from the
   source, specifically so it can be located automatically.
4. The browser renders each finding as a hoverable item. Hovering one loads the cited PDF (via
   Mozilla's **pdf.js**, vendored locally in `static/pdfjs/` — no CDN, fully offline) directly in the
   browser, searches its pages for the quoted text, jumps to the matching page, and draws a highlight
   over it. If the exact quote can't be located (the model paraphrased instead of quoting verbatim,
   which does happen), it says so and shows page 1 rather than pretending it found something.

## Data retention changed for this feature — read this

Earlier prototype versions deleted the uploaded zip and extracted PDFs the moment a request finished.
**That's no longer true.** The document viewer needs to serve the original PDFs back to the browser, so
extracted PDFs now stay in a session folder under the system temp directory until your *next* upload
replaces them (only the most recent analysis is ever kept — nothing accumulates indefinitely). They
still never leave this machine, but this is a real change from "nothing persists" to "the last run's
files persist until you run another one." Worth knowing before testing with anything sensitive.

## Known limitations (this is a prototype, not the real system)

- **OCR handles clean typed scans/faxes well, genuine handwriting poorly — benchmarked, not guessed.** Runs on GPU (Apple Silicon MPS, ~3-4x faster than CPU with identical accuracy) with deskew + auto-contrast preprocessing (the single biggest accuracy lever found — a ~4° skewed page went from 42% to 98% word accuracy; see `testing/ocr_benchmark.py` and `testing/ocr_results/benchmark_results.json`). Clean typed/faxed text: ~99% word accuracy. Legible print-style "handwriting": ~92%. Genuine cursive/connected handwriting: tops out around 50%, matching published figures for this class of OCR engine (non-AI, not a vision-language model) — a real capability ceiling, not a settings problem; a vision-language-model OCR (already noted as a future option in `PRODUCT_DEFINITION.md` §5/§6) would be needed for real handwriting. Any page that went through OCR is flagged in the warnings — treat those findings as lower-confidence.
- **No highlighting on OCR'd pages.** The document viewer highlights passages by searching the *actual PDF's* text layer via pdf.js. A scanned/faxed PDF has no text layer at all — the OCR text only exists server-side, for the model. So findings from an OCR'd page will show the source page but can't auto-highlight the passage; the viewer says so explicitly rather than silently failing.
- **Context window limits how much can go in at once.** The model runs with a 12288-token context (`LAWFIRMAGENT_NUM_CTX` env var to change it — larger uses more memory). If combined document text is too long, it's truncated and a warning says so rather than silently dropping content.
- **No verifier pass yet.** This is the single-model extraction step only — the generator/verifier two-model pattern from `PRODUCT_DEFINITION.md` §5/§6 isn't built here yet.
- **Quote-matching has an exact-match and a fuzzy fallback**, not full semantic search. If the model's quote doesn't appear verbatim (formatting quirks, minor paraphrase, punctuation/word-order drift), a longest-contiguous-word-run fuzzy match is tried before giving up; if that still fails, the viewer says so rather than guessing at a highlight.
- **Highlighting works at the level of whole text fragments**, not precise sub-character boundaries — it'll highlight the full text item(s) overlapping the match, which is sometimes a slightly larger box than the exact quoted phrase.
- **No persistent history beyond the current session.** Fine for testing, not for real casework.
- **Single Flask dev server, not production-grade.** Fine for local single-user testing; not meant to be exposed beyond `127.0.0.1`.
